# Changelog

All notable changes to this project are documented here.
Format based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [1.1.9-beta] - 2026-09-24

### Added
- **`scene_grid` tiles can now be highlighted off an arbitrary HA entity's state, not just the Activity-tracking already there.** The existing Activity-based border-highlight (a tile with `"activity"` or `"track"`+`"room"`) stays exactly as it was, and is now joined by a second, independent, combinable mechanism: the same `"state_entity"`/`"state_value"`/`"active_color"`/`"active_border"` fields already on `button_grid` (see its own class doc) — useful for a `scene_grid` tile that isn't an Activity at all, e.g. a plain navigation tile to a "Lights" page lit up while any light in the room is on. Unlike the Activity mechanism (border only), this one also changes the tile's *background* via `"active_color"`, same as `button_grid`. Web builder (`cards.js`): the `scene_grid` item form gained the same State entity/Target state/Active color/Accent border fields already on `button_grid`'s form.
- **Media player: when there's no artwork at all (not just an external-URL loading failure — see the Fixed entry above), the full-card placeholder now shows the active app's name (`app_name`) under the cast icon.** Previously a bare, unlabeled cast icon regardless of which app was active. No change to the compact/tile header's small circular avatar (too small to fit a label). This doesn't retrieve an actual per-app icon: neither Home Assistant's Apple TV integration nor its docs appear to expose one (only `app_id`/`app_name` as plain text), so `app_name` is the most specific thing there currently is to show.
- **`button_grid` buttons couldn't close a popup after their action — `"closePopup": true` was silently ignored.** An oversight in the Harmony/IR support added just above: `fire()` never read `"closePopup"` at all (and the web builder's `button_grid` form didn't even show the checkbox), even though it's exactly as applicable to a `button_grid` button as to a `scene_grid` one — arguably more so, since `button_grid` is the natural fit for a TV/Projector source-picker popup. `fire()` now checks `"closePopup"` last, after every other action on the button, same as `scene_grid`'s own. Web builder: the `button_grid` item form gained the same "Close the open popup after this button's action" checkbox already on `scene_grid`'s form.
- **Web builder: a page opened as a popup only by a tile (not `linkedPage`/`openWhenEntity`) can now have its own popup size/position, in the builder and on JSON import.** The page dialog's popup width/height/position row, and `normalizePageFromJson`'s JSON-import path, only ever showed/kept those fields when the page itself had `linkedPageMode: "popup"` or `openMode: "popup"` — neither of which a page that's *purely* opened via a tile's own `"pageMode": "popup"` (added above) has, since that trigger lives on a tile on some *other* page, invisible to this page's own dialog. Editing such a page in the builder silently ignored any popup size already in the JSON, and re-saving it from the builder would drop it outright. Added a new standalone checkbox, "Opened as a popup from a tile elsewhere on the dashboard", next to the existing "Linked page"/"Auto-open" popup-mode pickers — checking it reveals and persists the same width/height/position fields independent of the other two triggers. `normalizePageFromJson` (the paste-box and device-load import path) now keeps `popupWidth`/`popupHeight`/`popupPosition` whenever present on a page, rather than only when `linkedPage`+`linkedPageMode: "popup"` were also both set, and the dialog now pre-checks the new checkbox itself when it detects that case on open (saved geometry present with neither other trigger set to popup).
- **`button_grid`: a button can now fire a direct Harmony command/Activity or a local IR command, not just an HA service call.** Previously `button_grid` was hard-wired to a plain `service` call (see `ButtonGridCard.kt`'s old doc: "each firing a HA service call") while `scene_grid` had the richer action set — an inconsistency there was no real reason for. `fire()` now fires every action a button carries independently: `service` (unchanged, now optional), a direct Harmony device command (`harmonyDevice`+`harmonyCommand`, optionally `hub`), a direct Harmony Activity start (`activityId`, optionally `hub`), and/or a local IR command (`irDevice`+`irCommand`, no hub needed) — same fields, same behavior as `scene_grid`'s own Harmony/IR options, just without `scene_grid`'s page/composed-Activity/tracking options, which don't apply to a plain action button. A button can combine more than one (e.g. call an HA service *and* send a direct IR command in the same tap). Web builder (`cards.js`): the `button_grid` item form gained the same Harmony action picker and IR device/command fields already used on `scene_grid`, reusing the existing `giHarmonyMode`/`giIrDevice` widgets rather than duplicating them; a button now needs at least one of Service/IR/Harmony set, validated on save.
- **Open a page as a popup from a normal tile, and optionally close it again after an action.** Until now the floating popup overlay (`LinkedPagePopup`) could only be triggered by a `linkedPage` swipe-up or by `openWhenEntity`+`openMode: "popup"` — a `scene_grid`/`title` tile's own `"page"` always did a full pager navigation. `CardContext` gained `openPagePopup(pageName)` and `closePopup()`, built in `Dashboard()` from the exact same `linkedPopupPage`/`popupOpenedByEntityId` slot the other two triggers already share (so only one popup is ever on screen, however it was opened), reusing the target page's own `popupWidthFraction`/`popupHeightFraction`/`popupPosition` — same as `openWhenEntity`. New per-tile options: `"pageMode": "popup"` next to `scene_grid`'s existing `"page"` (and `"${prefix}_pageMode"` for `TitleCard`'s `title_page`/`subtitle_page`) opens it as a popup instead of navigating; `"closePopup": true` (and `"${prefix}_closePopup"`) dismisses whichever popup is currently open, fired after every other action on that tile — e.g. a small TV/Projector popup where tapping one source tile sends the IR/Harmony command *and* closes the popup in the same tap. `closePopup` is independent of `page`/`pageMode` on the same tile, so a tile elsewhere can open the popup while a different tile inside it closes it. Web builder (`cards.js`): the grid-item dialog's "Page to open" field gained a page/popup mode selector and a "Close the open popup after this tile's action" checkbox.
- **Whole-card focus outline for D-pad navigation.** With several cards stacked on one page, it was hard to tell which card you were in — only the individual focused button/tile got a highlight. `Dashboard.kt`'s `RenderCard` (where every card gets rendered onto a page) now wraps each card in a `Box` that draws a `theme.accent` outline around the *entire* card while D-pad focus is anywhere inside it, on top of that button/tile's own highlight. Uses Compose's `onFocusChanged { it.hasFocus }` — true for this node or any focused descendant — so no changes were needed in any individual card's own file.
- **`scene_grid`: configurable icon position, same as `button_grid`.** New grid-wide `iconPosition` card option (`"top"` (default, unchanged) / `"bottom"` / `"left"` / `"right"`) — `SceneGridCard.kt`'s icon+label tile shape now lays out as a `Row` (left/right) or `Column` (top/bottom) accordingly, via two new `IconLabelRow`/`IconLabelColumn` composables mirroring `ButtonGridCard`'s own `GridButtonRow`/`GridButtonColumn`. Only affects tiles showing both an icon and a name; has no effect on icon-only tiles (`"show_labels": false`) or on `"icon_fill"` tiles, neither of which has a label to position against. The shared `IconPosition` enum (and a shared `parseHexColor()` helper) moved out of `ButtonGridCard.kt` into a new `GridCardSupport.kt`, so both cards read the exact same four positions instead of maintaining two copies. Web builder: the existing "Icon position" selector on the grid form is now shown for `scene_grid` too, not just `button_grid`.
- **`button_grid`: conditional styling driven by a Home Assistant entity's state.** A button can now change its background color and/or draw an accent border while a chosen entity is in a given state — e.g. highlighting whichever source is currently selected on an `input_select`, or which input a TV/receiver is on. New per-button fields: `state_entity` (the entity to watch), `state_value` (a target state, or a list of states — active on any match), `active_color` (background while active, same hex format as `scene_grid`'s `"color"`), and `active_border` (`true` for the theme's accent color, or your own hex color). Conceptually the same mechanism `scene_grid` already uses to border-highlight the currently active Activity, just driven by an arbitrary entity/state instead of `ActivityRuntime`. A button without `state_entity` renders exactly as before. Web builder: new "State entity" / "Target state" / "Active color" / "Accent border while active" fields on the `button_grid` item form.
- **ConfigServer: Added a self-healing loopback watchdog supervisor (#69).**
Introduced a dedicated `ConfigServerSupervisor` that probes the local endpoint (`http://127.0.0.1:8080/current-page`) every 30 seconds. If HTTP requests stall or timeout on background threads (a known edge-case on legacy hardware like HA100 / Android 8.1 panels), the supervisor detects 3 consecutive failures and gracefully restarts *only* the `ConfigServer` lifecycle after a 500ms delay. Enforces a 120-second cooldown period and safely shuts down when the server is disabled, settings reload, or the Activity is destroyed. Thanks to [DimpOne](https://github.com/DimpOne) for the contribution! 🙏
- **Web builder: a "← Accueil" link back to the devices catalog (`/`) at the top of `/builder/`.** Previously the only way back was editing the URL by hand.
- **Web builder: reorder a `scene_grid`/`button_grid`'s tiles.** `renderGridItemsList()` (`cards.js`) gained ↑/↓ buttons next to each tile (new `moveGridItem()`), swapping it with its neighbor — chosen over HTML5 drag-and-drop for reliability on tablet/touch.
- **Media Browser: long-press a playable — or Apps/Radios-style "expandable but actually a dead end" — row for "Play" / "Add to queue".** `MediaRow` now uses `combinedClickable`; a long-press on anything with `can_play` **or `can_expand`** opens a small popup ([`R.string.media_browser_play`]/[`R.string.media_browser_add_to_queue`]). "Play" behaves exactly like the existing tap-to-play (closes the browser); "Add to queue" calls the new `HaClient.playMedia(..., enqueue = "add")` overload (mirrors `media_player.play_media`'s own optional `enqueue` field: `"add"`/`"next"`/`"play"`/`"replace"`) and deliberately leaves the browser open so more items can be queued in a row. Extending this to `can_expand` items too (not just `can_play`) is the concrete fix for the LMS/Lyrion "Apps"/"Radios" investigation below — Home Assistant's own frontend debug logs confirmed the integration marks leaf, directly-playable radio stations as `can_expand: true, can_play: false` regardless, so a short tap in Astrion (which, correctly, tries to browse into a `can_expand` item first) dead-ends into an empty folder for exactly these entries; long-press is now the escape hatch, mirroring what Home Assistant's own frontend does by resolving-and-playing them outright instead of insisting on `can_expand`.
- **`button_grid`: configurable icon position.** New `iconPosition` card option (`"top"` (default, unchanged) / `"bottom"` / `"left"` / `"right"`) — `ButtonGridCard.kt`'s `GridButton` lays the icon+label out as a `Row` (left/right) or `Column` (top/bottom) accordingly. Web builder: new "Icon position" selector on the `button_grid` form.
- **A clearly visible focus border when navigating with the physical remote's D-pad, instead of the stock ripple's barely-there darkening.** `Modifier.tapClickable` — the shared tap helper used by nearly every card in the app — now tracks its own focus state and draws a `theme.accent` border around itself while focused via keyboard/D-pad (a touch tap never sets this; it's specifically for "which tile is the cursor on" when moving with UP/DOWN/LEFT/RIGHT). An optional `focusShape` param lets a caller match its own corner radius (wired up for `button_grid`, `scene_grid`, and the media player's circular/rounded controls) — everywhere else still gets a visible rectangular border by default rather than nothing. This replaces the originally-planned "highlight the selected/active scene tile" reading of this request, which turned out not to be what was meant; that accent-bordered "currently active Activity" tile from earlier in this same session is a separate, still-present addition (see below).
- **`scene_grid`: the tile representing the Activity currently active in its room gets a visible accent border.** New `ActivityRuntime.isActiveTile(scene, activeByRoom)` (read-only counterpart of `trackTap`'s id derivation, reused via `activityFrom`) — `SceneGridCard` collects `activeByRoom` reactively (`collectAsState()`) and border-highlights whichever tile (composed Activity or `track: true`) currently matches, across all three tile shapes (icon-fill, icon+label, text-only). Previously there was no visual indication at all of which scene/Activity tile you'd actually landed on after a tap.
- **`linkedPage` can now open as a popup instead of a full-page jump.** New `PageConfig.linkedPageMode` (`"page"` default, unchanged, or `"popup"`), `popupWidthFraction`/`popupHeightFraction` (0–1, default 0.7/0.5), `popupPosition` (`"center"`/`"top"`/`"bottom"`/`"left"`/`"right"`). In popup mode, swiping up renders the linked page's own cards (`PageContent`, reused as-is) inside a new `LinkedPagePopup` overlay floating over the current page — the pager/navigation stack is never touched, so it's purely cosmetic on top of whatever page is on screen. Dismissed by tapping the dimmed backdrop or its own ✕; a tap inside the popup itself is swallowed so it doesn't fall through. `DashboardLoader.kt` round-trips the new fields (`linkedPageMode`/`popupWidth`/`popupHeight`/`popupPosition`); an existing `dashboard.json` with none of them keeps working exactly as before. Web builder: "How it opens" (Full page / Popup) selector on the linked-page picker, with width/height/position fields shown only in popup mode.
- **`media_player` (full variant): configurable artwork fit + shape.** New `artwork_fit` (`"cover"` default, unchanged / `"contain"`) and `artwork_ratio` (`"square"` default, unchanged / `"portrait"`, 2:3) card options — movie/TV posters no longer have to be cropped top/bottom to fit a near-square `Crop`'d tile. Web builder: "Artwork fit"/"Artwork shape" selectors on the `media_player` form, shown only in the "Full" variant (the only one this affects).
- **A temporary volume popup on VOLUME_UP/VOLUME_DOWN/MUTE.** Whenever one of these hardware-key hotkeys fires a real Home Assistant service call against an entity (not the Harmony/IR-direct branches, which have no queryable state), `MainActivity.runHotkey()` now also sets a new `VolumeHotkeyTrigger(entityId, nonce)` (`DashboardNavigation.volumeHotkeyTrigger`). New `VolumePopupHost` (`Dashboard.kt`) shows a small floating bar (icon + level bar + `N%`, or "Muted") reading the entity's `volume_level`/`is_volume_muted`, auto-dismissing itself after ~2.2s and restarting that timer on every repeat press (the trigger's `nonce` guarantees `LaunchedEffect` sees a fresh key each time, even for the same entity). Home Assistant's `media_player.volume_level` is always a normalized 0–1 float, never decibels, so this shows a percentage rather than dB — no generic HA attribute exists to read a real dB value from for an arbitrary AV receiver integration.
- **`openWhenEntity` can now open as a popup instead of navigating away from whatever page you're on — ideal for an intercom/doorbell.** New `PageConfig.openMode` (`"page"` default, unchanged, or `"popup"`), sharing the exact same `popupWidth`/`popupHeight`/`popupPosition` fields `linkedPageMode: "popup"` already uses — a page's popup shape is one property, regardless of which of the two mechanisms opens it as one. `DashboardEntityPageEffect` (which already watched `openWhenEntity`/`openWhenState`/`closeWhenState` to auto-navigate) now shares one popup slot with the manual `linkedPage` swipe-up path: a new pure `resolveEntityPageAction` helper decides, per page and per tick, whether to open/close a popup or navigate a full page, and — critically — only ever auto-closes a popup if the *same* entity that opened it is the one now leaving its trigger state, so it never dismisses one you opened by hand via `linkedPage`, or one a *different* entity opened. Web builder: a "How it opens" (Full page / Popup) selector under "Auto-open when...", sharing the same width/height/position fields already shown for `linkedPage`'s own popup mode.
- Italian localization support. Thanks to [@dvbit](https://github.com/dvbit) for the contribution! 🙏
- **Automated page routing via Home Assistant entities** (`PageConfig.openWhenEntity`) — a page can now declare an explicit entity ID string to monitor. When this entity changes state or triggers, the dashboard can automatically bring this page to the foreground (e.g., flipping automatically to a "Weather" or "Meteo" page when rain is detected, or showing a camera stream page when a doorbell rings). `DashboardLoader.kt` properly parses and round-trips the optional `"openWhenEntity"` field from `dashboard.json`, mapping it cleanly at runtime to `openWhenEntityPages` without risking crashes or regressions on older configurations.
- **Linked pages** (`PageConfig.linkedPage`) — a page can now name another page to jump straight to on a swipe UP from its own [`PageIndicator`], the vertical counterpart of the existing horizontal `parent`/`parentKey` relationship. Meant for a per-card "more options" page (e.g. extra Apple TV controls) sitting just below whatever card it belongs to: give the linked page its own `parent` pointing back, and BACK/its chevron/the tap-to-return flow already in place works unchanged. `DashboardLoader.kt` round-trips an optional `"linkedPage"` field; existing `dashboard.json` files with none keep working unchanged. Web builder (`docs/index.html`/`js/pages.js`): new "Linked page" picker on the page dialog, renamed/deleted pages keep every `linkedPage` reference in sync the same way `parent` already did.
- **Conditionally-hidden pages** (`PageConfig.hiddenUnlessActivity`) — a page's dot can now be left out of `PageIndicator` until a specific Activity is actually running (same id space as a scene_grid tile's own `"activity"` field, picked from the same dropdown), reappearing automatically the moment it is and disappearing once it stops — decluttering the indicator for a page tied to a device that isn't always in use. Deliberately dots-only: the pager itself (`pageCount`/`pagerState`/`navTarget`/`navigateToPage`) always covers every page in `AppConfig.pages`, unfiltered, regardless of this field — an earlier version of this feature gated the pager itself on live Activity state, which raced a scene_grid tile's own "activity"+"page" combo tap and silently broke navigating to a page right as its Activity started (`ActivityDispatcher.switchActivity` only calls `markActiveById` — what this field actually reads — *after* every device command in the plan has gone out, well after the tile's own synchronous tap handler had already given up looking for a still-hidden page). `Dashboard.kt` computes a lightweight `activeActivityIds` set (`ActivityRuntime.activeByRoom`'s non-null values) purely for `PageIndicator` to filter dots with; nothing else touches it. `DashboardLoader.kt` round-trips an optional `"hiddenUnlessActivity"` field. Web builder: new "Hide unless this Activity is running" picker on the page dialog, sourced from the Activities tab (same list/format as a scene_grid tile's own activity picker in `cards.js`).
- **A scene_grid tile starting an Activity now navigates through that Activity's own `page`, not a redundant field on the tile.** `ActivityDispatcher.switchActivity` calls the new `navigateToPage` it's constructed with right after `markActiveById` — i.e. once the Activity is actually confirmed active, not speculatively before any of its device commands have gone out. `SceneGridCard`'s own `onTap` no longer fires a tile's `"page"` field when that same tile also sets `"activity"`: this is what `ActivityConfig.page` was already designed for (the web builder's `cards.js` already auto-syncs a scene_grid item's `activity` field into `activity.page` whenever a card sets one — see `addGridItem`'s existing comment on that), and letting `ActivityDispatcher` fire it at the right moment is what actually fixes the redundant-and-racy pattern of a tile navigating on its own, rather than the field rename above merely making the symptom (a silently un-hidden page) go away. A tile's own `"page"` still works exactly as before on any tile that doesn't also set `"activity"`.
- **"Open Settings" needed no new code at all — it already existed as a regular hotkey action.** `openOverlay: "settings"`/`"activities"` (`hotkeys`/`longHotkeys`, global or per-page, any key, either press length) was already fully wired end-to-end (`ConfigServer`, `MainActivity`'s hotkey engine, the Hotkeys tab's own `openOverlay` UI in `hotkeys.js`) — the only thing actually missing was that the real device POWER button can't be bound to anything at all (Android's window manager intercepts every real `KEYCODE_POWER` press — short, long, even double — before any third-party app, even a Device Owner one, ever sees it; not fixable from an app, full stop), and this app's own on-screen POWER tile is already spoken for (`HardwareKey.POWER`, raw code 132 — a genuinely deliverable KeyEvent, just tied to a software control, not the physical button) — it's what a dashboard uses to turn its own AV devices on and off, so it must stay untouched. No restart feature was added either: the device's real side button already does that natively (Android's own short-press-sleep/long-press-restart-or-power-off), which is exactly the "official, like every Android device" behavior wanted in the first place — nothing to build there. `hotkeys.js`'s `openOverlay` picker had two stale labels left over from *before* Activities and Settings swapped gesture spots (see the very next entry below) — those are fixed. Pick any key that isn't POWER from the Hotkeys tab, `openOverlay: "settings"`.
- **Astrion IR Extenders** (network-connected WiFi IR blasters, see the astrion-ir-extender project) as a full alternative to the device's own built-in IR blaster, for commands that need to reach a closed cabinet or another room. No Home Assistant required.
  - `IrDeviceConfig` gains a `target` field (`IrTarget.Local` — the existing `ConsumerIrManager` behavior, still the default — or `IrTarget.Extender(extenderId)`). Lives on the IR device itself, not on individual cards/hotkeys, since a device is physically in one place: point a device at an extender once, and every card/hotkey/Activity that already references it automatically follows. `DashboardLoader.kt` round-trips an optional `"target"` field; every existing `dashboard.json` with none keeps working unchanged.
  - New `ExtenderConfig` (`RemoteSettings.extenders()`/`saveExtenders()`, mirroring Harmony hub storage), `ExtenderClient`/`ExtenderRegistry` (`com.custom.astrion.extender`) — plain-HTTP client posting to an extender's `POST /pronto`.
  - **Batched, sequenced sends**: `ExtenderClient.sendBatch()` posts several Pronto codes — each with its own delay-before-transmit — in a single request, instead of one HTTP round-trip per command. `ActivityDispatcher` (extracted from `Dashboard.kt`; see Changed below) builds an ordered `StepPlan` for an Activity switch/stop and merges consecutive same-extender steps into one batch, while local IR/Harmony/HA steps still dispatch individually with a real delay — this is what actually fixes commands silently going missing when two arrive close together on the same extender (e.g. switching Activities that share one), which a naive one-request-per-command design couldn't guarantee.
  - `IrStepConfig` gains an optional `pronto: String?` — the original Pronto hex string a resolved step was decoded from, when known, forwarded to an extender as-is instead of re-deriving it from the already-decoded `freq`/`pattern`. Populated for ir-database (`SdCardRef`) devices; **not yet populated for `Inline`-sourced devices** (dashboard.json only persists their decoded `freq`/`pattern` today) — those log a warning and no-op rather than send anything if pointed at an extender.
  - Web builder: new "IR Extenders" section (`devices.html`/`devices-page.js`) — add/edit/remove extenders by name + IP/hostname + MAC address, same all-or-nothing save as the Harmony hubs section. `localId` is derived from the MAC (`ext_<mac>`, normalized regardless of how it's typed — colons, dashes, or none), guaranteeing the same physical unit keeps the same id across a rename, IP change, or remove-and-re-add — the MAC field is required specifically to make this possible; an earlier attempt at deriving the id from a MAC-suffixed mDNS hostname string never actually worked (ESPHome's `name_add_mac_suffix` appends only 6 hex digits, not the 12 the matching regex expected). New "where should this device's commands actually get sent from?" selector on the IR device editor, writing `target` in the format above; blocked for hand-pasted ("inline") commands with an explanation, since those can't target an extender yet (see `IrStepConfig` above).
  - `ConfigServer.kt`: `parseExtenderRows()` wired into `handleSaveConnection()`; `GET /devices-config` now includes `extenders`.

### Changed

- **"Active Activities" overlay moved from the bottom page-indicator's swipe-up onto the top status bar's swipe-down** — the spot Settings used to occupy, now that Settings is just a regular assignable hotkey instead of a fixed gesture. `TopStatusBar`'s callback renamed `onSwipeDownToSettings` → `onSwipeDown` to match (it's the caller's choice now, not baked into the name); `PageIndicator`'s `onSwipeUpToActivities` renamed `onSwipeUpToLinkedPage` since swipe-up now drives the new linked-page feature above. `ActivitiesOverlay`'s own dismiss gesture strip moved from top (swipe down) to bottom (swipe up) to match — closing it now pulls it back out the way it came in, the same convention `SettingsOverlay` already used.
- `DashboardLoader.kt` now actually parses a page's `"parentKey"` field from `dashboard.json` — it was documented as configurable but silently ignored, every page defaulting to `"BACK"` regardless of what was saved. Found while adding the two new page fields above; unrelated to them otherwise.
- `HardwareKeyRouter` gains `isLongBound()`, mirroring the existing `isShortBound()` — general-purpose, for any future fallback binding that needs to check long-press the same way the parent-key fallback already checks short-press.
- `Dashboard()`'s IR/Activity dispatch logic (`sendIrCommand`, `dispatchActivityCommand`, `dispatchActivityPower`, `switchActivity`, `startActivity`, `stopActivity`) extracted into a new `ActivityDispatcher` class (`com.custom.astrion.ui`) — behavior-preserving except for the batching described above, which only this extraction made practical to add cleanly.

### Fixed

- **Media artwork not loading for players whose `entity_picture` is a raw external URL (e.g. Yandex Station's `avatar.mds.yandex.net` link).** `MediaPlayerCard` only ever read `entity_picture`, and `HaClient.fetchBitmap`/`fetchBytes` always attached the HA bearer token to whatever URL that resolved to — fine for the common case where `entity_picture` is itself an HA-relative path (`/api/media_player_proxy/…`, e.g. Apple TV), but for a player whose `entity_picture` is instead a genuinely external CDN URL, that HA token got sent to a third-party host that never asked for it, which some external hosts reject outright. Two independent fixes: `MediaPlayerCard` now prefers `entity_picture_local` (Home Assistant's own locally-proxied, always-HA-relative copy of the artwork, when the integration provides one) over `entity_picture`, falling back to the latter only when no `_local` variant exists — unchanged behavior for every entity that never had one. And `fetchBitmap`/`fetchBytes` now only attach the bearer token when the resolved URL actually targets this HA instance (relative, or absolute on `baseUrl` itself), never to a genuinely external host, as a second layer of defense (and to stop leaking the HA token to third-party servers for no reason).
- **D-pad focus outline stayed on a tile/card even when every directional D-pad key was consumed by a configured hotkey**, making it look like a movable cursor that in fact couldn't move on that key anymore. `MainActivity.dispatchKeyEvent` now clears Compose's focus the moment a directional key (UP/DOWN/LEFT/RIGHT — CENTER excluded, it's an activation key, not a move) is consumed as a hotkey instead of reaching Compose's own focus-navigation, via a new `clearFocusTrigger` state observed once in `composeContent`'s `LaunchedEffect`. Unmapped D-pad keys are completely untouched — normal focus-navigation and its outline still behave exactly as before.
- **Web Builder: disabling every Volume control on a `media_player` card and saving reverted to the default set when the card was reopened.** `o.volume_controls || 'mute,buttons'` in both `cards.js` (the item-edit form) and `preview.js` (the live preview) treated an explicitly-saved empty string (`"volume_controls": ""`, meaning "no controls") as if the key were absent, falling back to the default — a classic JS falsy-string bug. Both now use `??` instead of `||`, which only falls back when the key is truly `null`/`undefined`. Runtime behavior was already correct (the bug was builder-only, read/write).
- **Circular buttons showed a square focus highlight when navigating with the D-pad.** `Modifier.tapClickable`'s `focusShape` parameter (added with D-pad focus support) needs the caller to pass `CircleShape` explicitly on a round button — otherwise it silently falls back to a rectangle. That fallback was actually hit almost everywhere: only one of the app's ~25 circular buttons had it wired up correctly. Fixed across `SpeakerGroupCard.kt`, `LightCard.kt`, `MediaPlayerCard.kt`, `PictureElementsCard.kt`, `MediaPlayerDetailDialog.kt`, `TvRemoteCard.kt`, `AppleTvRemoteCard.kt`, `FanCard.kt`, `VacuumCard.kt`, `Dashboard.kt` (page dots), `LightDetailDialog.kt`, `CoverCard.kt`, and `ClimateCard.kt` — every circular tap target now gets a matching circular focus outline. A few pill/rounded-corner buttons found along the way (e.g. the Apple TV remote's pill buttons, `ClimateCard`'s mode chips) got their `focusShape` corrected to match their own shape too, for the same reason. Purely visual — none of these targets were actually broken to tap or click, only the D-pad focus ring's shape.
- **Apps/Radios navigation could dead-end two different ways, both confirmed with real device debug logs during this investigation: a leaf station sometimes marked `can_expand: true` with nothing underneath, and — the more stubborn one — a genuine sub-folder sometimes marked `can_expand: false` despite having real children.** The first is handled by the empty-folder-falls-back-to-play fix below. The second needed its own fix: a short tap's `onClick` now has a third branch, scoped the same way (`isAppsOrRadiosContentType` — `"radios"`, `"apps"`, or any `"app-*"` node under either), that tries to browse into the item anyway when it's neither `can_expand` nor `can_play`. If that guess was wrong and it really was a dead end, the existing empty-folder fallback catches it and plays the item instead — so between the two, an Apps/Radios item is never just inert on tap, whichever way this integration happened to mismark it. Neither change affects any other content_type, where both flags stay fully trusted.
- **Tapping into an Apps/Radios entry that turns out to be a leaf (no children) left the user looking at an empty "Nothing here" screen instead of just playing it.** The long-press escape hatch added earlier in this investigation works, but a plain short tap — matching how Home Assistant's own frontend behaves for these entries (confirmed via its debug logs) — is the more natural fix. `MediaBrowser`'s reload effect now detects a genuinely empty result for a non-root folder **whose `content_type` is `"radios"`, `"apps"`, or any `"app-*"` node under either** — the exact content_type pattern Home Assistant's Squeezebox/Lyrion integration uses for this category, at any depth, since a node's content_type carries down unchanged to all of its descendants — and falls back to calling `HaClient.playMedia()` with that same folder's `content_id`/`content_type` directly, closing the browser, instead of leaving an empty screen up. Scoping this to Apps/Radios specifically (rather than any empty folder anywhere) means a genuinely empty folder elsewhere in the library — an empty Favorites list, say — still shows "Nothing here" as expected, and real multi-level Apps/Radios structures on other integrations/setups keep working exactly as before; the long-press option from earlier stays available too, for a non-empty folder the user wants to queue/play as a whole rather than open.
- **`media_player/browse_media` used the same general 8s response timeout as every other websocket request, silently timing out on large folders (hundreds of entries, each with its own icon URL) — confirmed for Home Assistant's Squeezebox/Lyrion "Apps"/"Radios" listing — while a small local-library folder (an album's tracks, say) loaded fine within it.** This is what was actually behind "Apps/Radios stop, but browsing an album works fine" — not (only) the `can_expand`/leaf-station mismatch fixed above. `HaClient.browseMedia()` now uses its own, much longer 25s timeout (`MEDIA_BROWSE_TIMEOUT`), separate from the 8s `RESPONSE_TIMEOUT` still used for quick service calls elsewhere. The Media Browser already shows a spinner while a folder is loading, so the longer wait is visible, not silent.
- **Changing the linked-page popup's page/mode/size/position (or, more broadly, anything about `linkedPage` on any page) required a full app restart to take effect, even though `dashboard.json` itself was updated correctly and hot-reload ran.** `PageIndicator`'s swipe-up gesture detector uses `.pointerInput(Unit)` so an in-progress drag never gets cut off by an unrelated recomposition — but that also means its suspend block's closure over `onSwipeUpToLinkedPage` is captured exactly once, at `PageIndicator`'s first composition, and never again: since `PageIndicator` itself stays mounted across a `dashboard.json` reload (only its parameters change), that first-captured closure — and whatever `linkedPage`/`linkedPageMode`/`popup*` values it closed over — was permanently stuck until the whole Activity was recreated. Fixed with `rememberUpdatedState`, which keeps the same long-lived gesture coroutine (no interrupted drags) while always resolving through to the latest recomposition's actual callback.
- **`linkedPage` popup always used the default size/position (0.7/0.5/"center"), ignoring the source page's own `popupWidth`/`popupHeight`/`popupPosition`.** `onSwipeUpToLinkedPage` was reading those three fields off the *linked* (target) page's `PageConfig` instead of the *current* (source) page's — the one that actually declares `linkedPageMode: "popup"` in `dashboard.json`. Since the target page generally has no popup settings of its own, every popup silently fell back to the defaults no matter what the source page's JSON said. `LinkedPagePopup` now takes a small `LinkedPagePopupState` bundling the target page (content) with the source page's geometry (size/position), so editing a page's `popupWidth`/`popupHeight`/`popupPosition` actually takes effect.
- **`DashboardLoader` never read `PageConfig.openWhenState`/`closeWhenState` back from `dashboard.json`.** The web builder already wrote both correctly, and `Dashboard.kt` already consumed them correctly — but the loader itself only parsed `openWhenEntity`, silently leaving `openWhenState` at its `"on"` default and `closeWhenState` at `null` regardless of what the file actually said. A page configured to open on some state other than `"on"`, or with an explicit close condition, behaved as if neither setting existed. Now parsed (and round-tripped on save) alongside `openWhenEntity`.
- **Editing an existing IR device from the "Devices" page silently duplicated it instead of updating it.** `editIrDevice()` set `editingIrDevice` *before* calling `openDeviceForm('ir')`, which calls `cancelIrDeviceEdit()` internally and resets it straight back to `null` — so `saveIrDevice()` always thought it was creating a new device. Found while wiring the extender target selector into the same form. Fixed by setting `editingIrDevice` after `openDeviceForm()` returns instead of before.
- **The builder's "Install on this device" button always installed the beta, even when the page was advertising an official update, leaving the official version stuck on the old one.** `loadStableBadge()` only ever rendered a manual download link for the official release; `toggleBetaBadge()` was the only badge wired to a real one-tap install button (`installBetaUpdate()` → `POST /install-beta-update`), so it was the only working button on the page regardless of which version the user actually meant to install — the official `POST /install-update` route (`ConfigServer.handleInstallUpdate()`) has existed since it was added but was never called from any client code. `loadStableBadge()` now gets the same button, wired to a new `installStableUpdate()` (`POST /install-update`); official and beta buttons now say "Install this official update" / "Install this beta update" (`installOfficial`/`installBeta`) instead of sharing one ambiguous label.
- **Harmony IR commands sent to the hub didn't match the button actually pressed, so some (or most) buttons silently did nothing.** `HarmonyHubClient.parseConfig()` used a Harmony device's `function.name`/`.label` fields as the literal IR command sent via `sendCommand()` — but those are just the hub's own display labels and can differ from the real command it expects (e.g. a button labeled "Select" whose actual IR command is `"OK"`, nested inside the function's `action` field as `{"command":"OK",...}`). Sending the display label instead of the real command meant the hub simply ignored it — no error, no feedback, just a dead button. `parseConfig()` now extracts the command from `action.command` when present, falling back to `name` only if `action` is missing or malformed; `label` still drives what's shown in the UI. Split `parseConfig()` into smaller `parseDevices()`/`parseDevice()`/`parseFunctions()`/`parseCommand()`/`extractIrCommand()`/`parseActivities()` helpers along the way — the added branching pushed cyclomatic complexity past detekt's threshold in one function.
- **A Harmony hub's `localId` changed every time it was removed and re-added, even for the exact same physical hub, orphaning any hotkey or scene tile referencing it.** `saveHarmonyHub()` (web configurator, `/`) generated a random `localId` (`'hub_' + Date.now()... + Math.random()...`) for every new hub row, with no link to the hub's own identity. Deleting a hub and adding it back — same IP, same Logitech `hubId` — produced a brand-new `localId`, silently breaking every `dashboard.json` reference (`"hub": "hub_..."`) built against the old one. `localId` is now derived deterministically from the hub's own `hubId` when known (`'hub_' + hubId`), so re-adding the same physical hub restores the same `localId` and existing references keep working; only falls back to a random id when `hubId` isn't set yet (e.g. before running "Detect"). Same fallback logic mirrored server-side in `ConfigServer.kt`'s `parseHubRows()` for consistency. Not retroactive — hubs already carrying a random `localId` from before this fix aren't remapped.

### Fixed

- **Home Assistant losing control of page navigation and Activities while the remote is docked (regression in 1.0.9).** `/set-page` and `start_activity` appeared to work for ~5 seconds (the underlying state did change) then silently reverted, because `Dashboard()` — and with it the `LaunchedEffect(navTarget)` and the Activity start/stop callbacks that actually act on those state changes — was completely removed from composition while `chargeDockMonitor.state.isDocked` was true. Fixed by the overlay change above.
- **An Activity's own page association silently broke for any Activity created since the wizard's page field was removed above.** `Dashboard.kt`'s "Active Activities" overlay navigates to `activity.page` when you tap a running activity there (`tapClickable(enabled = activity.page != null)`) — a real runtime consumer of that field missed during the initial removal, which only checked `ActivityRuntime.kt`'s (unrelated, tracking-only) use of the same field. `addGridItem()` now also sets `activity.page` at the same point it writes volume hotkeys, so this keeps working without reintroducing the broken manual field.
- **IR command suggestions were always empty for an ir-database *reference* device in the Activity wizard.** `irDeviceCommandEntries()` still read a global (`irDeviceCommandHints`) that only ever existed in the old in-builder `ir.js`, removed when IR device management moved to the Devices page — the "known command ids" hints typed in while creating the device were silently never surfaced. Hints are now stored directly on the device object (`commandHints`, persisted in `dashboard.json`) and read from there by both the Devices page and the builder.
- **Card editor (and 4 other) modals in `/builder/` closing unexpectedly while picking an option from a `<select>` inside them.** The backdrop-click-to-close handler (`onclick="if (event.target === this) close()"`) could be triggered by the synthetic click some browsers/WebViews dispatch when a native `<select>` dropdown dismisses, even though the person's tap never touched the backdrop. Now requires the *press* (`mousedown`) to have also started on the backdrop, not just the click's reported target — a real backdrop tap always does, a select-dismiss artifact never does.
- **`closePreviewModal()` didn't exist** — referenced by a "✕ Close" button since before this release, on a modal nothing in the codebase currently opens. Not reachable in practice, fixed anyway rather than left as a dead reference now that the backdrop-click rewrite above also wires up its close handler.
- **Motion-wake false triggers and mid-use screen-off on the HA100** ([#49](../../pull/49) by [@ClemsonJeeper](https://github.com/ClemsonJeeper)). The accelerometer emits glitch samples on resume around `ACTION_SCREEN_OFF`, which the old single-sample detector (raw magnitude delta > 0.9) read as motion, waking the screen randomly; separately, the fixed ~15s screen timeout ignored ongoing accelerometer activity, so the screen could go dark mid-shake while still in hand. Detector rewritten to be gravity-referenced: each sample splits into tilt (angle vs. a gravity baseline, hard-reset after any >1s sample gap, EMA-smoothed 0.9/0.1 while settled) and linear acceleration (deviation from that baseline) — wakes on `tilt > 30°` OR `lin > 2.5 m/s²` held for 3 consecutive samples. A 1.5s warm-up after `ACTION_SCREEN_OFF` drops all samples outright, and samples with `|a| < 5 m/s²` are rejected (gravity alone guarantees ≥ 9.8), suppressing the resume glitch at its source. New keep-awhile-in-hand hold: while motion stays past half the trigger threshold, `FLAG_KEEP_SCREEN_ON` is held (re-armed per sample, released after 10s of calm), fixing the mid-use screen-off. Wakelock window 4s → 5s with early release at 4.5s (2s wake cooldown unchanged). `MainActivity` now launches `singleTask`. New `MotionWake`/`ScreenTimeout` logcat tags cover setup, warm-up/subfloor drops, the consecutive-sample counter and trigger, wakelock acquire/skip/release, screen on/off transitions, and a rolling ambient-noise summary.
- **Home Assistant intermittently couldn't reach the device while its screen was off** (`Cannot connect to host ...:8080 ... Connect call failed`, both the coordinator's own `/pages` poll and `astrion.set_page`/`start_activity` calls). `ConfigServer`'s listener thread was never actually stopped by the screen turning off (only `CameraCard`'s streaming does that, since [#32](../../pull/32)) — the real cause was Android's default Wi-Fi power management suspending the radio itself while the screen was off, with nothing in the app telling it not to. New **"Keep Wi-Fi awake"** switch in Settings (`MainActivity.kt`/`SettingsMenu.kt`/`CardContext`), **off by default**: acquires a `WifiManager.WifiLock` (`WIFI_MODE_FULL_HIGH_PERF`) while enabled, toggled live with no restart (mirrors the existing "Wake on motion"/"Local config server" switches). Deliberately not on by default — this is a battery-powered handheld remote that spends most of its time idle/screen-off, and the lock disables the radio's own power-save for as long as it's held, a real continuous battery cost during exactly that state. Worth turning on if you use `astrion.set_page`/`start_activity` or the push-webhook feature from Home Assistant while the screen would otherwise be off; leave it off otherwise. No new permissions needed (`ACCESS_WIFI_STATE`/`CHANGE_WIFI_STATE`/`WAKE_LOCK` were already declared for `WifiBootReceiver`/motion-wake).
- **Update notification never fired on a beta/debug install.** `SettingsMenu`'s "Mise à jour disponible" row, and the local config page's `/check-update` badge, always compared against the official `/releases/latest` — by design, but with no fallback, so a device running the `-beta` build (`versionNameSuffix`, see 1.0.3) could never be notified about a newer `dev-latest` push, only about a newer *official* release, which for an active beta tester may never come. Both now detect a beta build via `BuildConfig.VERSION_NAME.contains("-beta")` and check `dev-latest` instead in that case. Also: a failed check (network error, GitHub rate limit, misconfigured `REPO` constant) was silently swallowed in `SettingsMenu` with no feedback anywhere — indistinguishable from "genuinely up to date" — now logged via `Log.w("SettingsMenu", ...)` so it's visible in `adb logcat`.
- **Light/cover sliders snapped back to a stale value right after release** ([#35](../../pull/35) by [@ClemsonJeeper](https://github.com/ClemsonJeeper)). `LightCard` (brightness, color temp) and `CoverCard` (position, tilt) reset their drag override immediately on release, showing the old value until Home Assistant's `state_changed` event arrived; light brightness also showed a stale percentage while off. New shared `rememberDragFraction`/`TrackDragFraction` helper in `CardGestures.kt`, used by all three sliders, releases the override once the live value catches up — or immediately when the entity goes unavailable (e.g. a light turned off out-of-band, where catch-up can't otherwise fire at 0).
- **Oversized PNG icons caused severe scroll lag, and could silently fail to display at all** ([#38](../../pull/38) by [@ClemsonJeeper](https://github.com/ClemsonJeeper), fixes [#36](../../issues/36)). Icons were decoded via `BitmapFactory.decodeFile()` at full source resolution even though rendered at ~28dp — a 2170×550 source consumed several MB of bitmap memory plus a matching GPU texture, and sources larger than the 4096px GPU texture limit were silently dropped entirely by `OpenGLRenderer`. New `decodeIconSampled()` in `ui/IconLoader.kt` two-pass decodes (bounds-only, then sampled) targeting each card's actual rendered size — wired into `SceneGridCard`, `ButtonGridCard`, and `TitleCard`.
- **Camera cards kept streaming all night with the screen off, draining the battery ([#32](../../pull/32) by [@ClemsonJeeper](https://github.com/ClemsonJeeper)).** Since Astrion Custom is a HOME launcher, its Activity is never stopped just because the display times out — `CameraCard`'s `LaunchedEffect` (both live-stream and snapshot-polling modes) had no concept of screen state, so Compose kept recomposing and pulling frames indefinitely regardless. Root-caused via `dumpsys batterystats`: a 100%→22% overnight drain with the screen on for only 52s total, yet ~7h51m of CPU time and 2.59M WLAN TX wakelock acquisitions over the same 9.5h window. `MainActivity` now tracks screen-on state via an `ACTION_SCREEN_ON`/`ACTION_SCREEN_OFF` receiver, threaded down through `Dashboard(screenOn = ...)` → `CardContext.screenOn` (defaults to `true`, so anything not passing it explicitly is unaffected) → `CameraCard`'s `LaunchedEffect`, which now short-circuits to a no-op while the screen is off and leaves the last decoded frame in place so the card resumes showing something immediately on wake rather than flashing back to a placeholder.
- **`media_player` progress bar frozen except right after pausing ([#12](../../issues/12) reported by [@dskudrin](https://github.com/dskudrin)).** `currentMediaPosition()` used `Instant.parse()` on `media_position_updated_at`, which only accepts a literal `Z` for UTC — Home Assistant reports a numeric offset instead (`...+00:00`), so parsing always threw and was silently swallowed, falling back to the raw static position forever. Now parsed with `OffsetDateTime.parse()`, which accepts both forms. Fixes the progress bar in both the full-variant card and the long-press detail dialog, which share this function.
- **Progress bar not rebasing after a seek.** The per-second ticker's `LaunchedEffect` only restarted on entity/state/track changes, not when the server pushed a fresh position (e.g. a seek within the same track) — it kept ticking from its old captured baseline instead of the new one. Now also restarts on `media_position`/`media_position_updated_at` changes, in both the card and the detail dialog.
- **D-pad couldn't reach the Light tile at all.** `LightCard`'s tile used a raw `pointerInput`/`detectTapGestures` for tap-to-toggle and long-press-to-detail, which never enters Compose's focus system — a physical remote's D-pad had nothing to land on. Replaced with `combinedClickable`, plus a new shared `rememberLongPressKeyModifier` that restores long-press-to-detail for a *held* hardware key, which `combinedClickable`'s `onLongClick` only ever fires from a touch gesture on its own.
- **D-pad long-press-to-detail didn't work on Cover and MediaPlayer tiles either.** Same root cause and fix as the Light tile above, applied to `CoverCard`'s tile and `MediaPlayerCard`'s compact tile.
- **Hotkey `openOverlay` / `openCurrentActivityRoom` silently ignored.** `DashboardLoader.parseHotkey()` never read these two fields from `dashboard.json`, so any hotkey configured with `openOverlay: "settings"`, `openOverlay: "activities"`, or `openCurrentActivityRoom: "<room>"` loaded with both fields `null` — the physical button did nothing, neither opening the overlay nor jumping to the active Activity's page, even though the web editor generated valid JSON for both. `encodeHotkeys()` had the same gap on the write side. Both fields are now parsed and re-encoded like every other `HotkeyConfig` field.
- **"Hotkeys active on this page" badge showed nothing for `openOverlay`/`openCurrentActivityRoom` hotkeys.** `preview.js`'s `renderPreview()` used its own local `describe()`, never updated for these two actions, instead of `hotkeys.js`'s `describeHotkey()`. The JSON was already correct — only the badge's text was blank.
- **`UpdateChecker.isNewer()` false-positive on beta builds.** The `-beta` suffix added by `versionNameSuffix` broke the numeric version comparison (`"1.0.3-beta"` → the `3` was silently dropped, comparing as `1.0` instead of `1.0.3`), causing the update checker to report "update available" almost constantly on beta installs even when already up to date or ahead. Now strips any `-suffix` before comparing.

- `ActivityRuntime`: scans every page/hotkey for `track: true` items, and every entry in `AppConfig.activities`, once per `dashboard.json` load; tracks which Activity is active per room (`activeByRoom`), updated via `trackTap()` (right after `SceneGridCard` fires a single-action tile), `markActiveById()` (after a composed Activity finishes its start sequence), and `bind()` (mirrors a Harmony hub's *live* Activity state into the matching room, so an Activity started from elsewhere — another remote, an HA automation, the physical Harmony remote — shows up too).
- `HarmonyHubClient`: `currentActivityId`/`activityState` (`StateFlow`), populated from the hub's unsolicited `connect.stateDigest?notify` push frames (`activityId` + `activityStatus`, distinguishing "starting" from "running" — confirmed against several real hub captures) and from a new one-shot `getCurrentActivity()` request/response call made right after connecting, since the push only fires on the *next* change.
- `HarmonyHubRegistry.clientsByLocalId` — exposes every configured hub's client, not just the default one (`client()`), for callers like `ActivityRuntime.bind()` that need to wire up all of them.
- New "Active Activities" overlay: swipe **up** from the bottom edge (page-indicator dots) — the mirror gesture of the existing swipe-down-for-Settings — lists every currently active Activity grouped by room; tapping one jumps straight to its page. Reached only by this gesture, like Settings, so it never appears in the page pager or its dots.
- Builder: new "IR Devices" section — the community `ir-database/` cascade picker (category → brand → model → command) now feeds a per-device command registry instead of a one-shot macro; a "Import all commands from this model" button pulls every command from a picked model in one go (ids already present are left alone, so re-importing after a manual rename doesn't clobber it); a manual Pronto Hex paste path covers devices/buttons not in the database; each saved command can be renamed inline (✎, no browser `prompt()`, consistent with the rest of the builder).
- Builder: new "Activities" section — a page-by-page wizard for composed Activities, mirroring Logitech Harmony's own Activity setup flow rather than one long form: pick a type (just prefills a name) → name/room/icon/page → select devices (local IR, Harmony hub+device, or a bare HA entity id — mixable) → one screen per selected device for its power-on/power-off/input commands, on/off-cycle toggles, and a delay → which device handles volume → review (flags any device with no commands set — it would silently do nothing at runtime) → save. Editing an existing Activity jumps straight to the name/room screen. A device already added can be edited in place, not just removed and re-added.
- Volume routing for a composed Activity: after picking a volume device, a further screen picks its volume-up/volume-down/mute commands (skipped for an HA device — it always uses the fixed `media_player.volume_up`/`volume_down`/`volume_mute` services). On save, if the Activity has a `page`, these are written as page-scoped hotkeys on it (`PageConfig.hotkeys`, which already override global bindings while that page is on screen — no new runtime mechanism needed). If that page already has a hotkey on `VOLUME_UP`/`VOLUME_DOWN`/`MUTE`, the builder confirms before overwriting rather than silently taking priority over an existing binding.
- `HotkeyConfig` gained `irDevice`/`irCommand` (send a local IR command directly from a physical-button binding, same as a `scene_grid` tile already could) and `devices` (a bookkeeping hint — see next point).
- `TrackedActivity`/`HotkeyConfig`/scene_grid items gained an optional `devices` list: which physical devices an Activity is known to involve, independent of whether it's composed or a lightweight `track`-only tile. `switchActivity()` in `Dashboard.kt` now reads this from *whatever* Activity was previously active in a room — Harmony-backed or composed — instead of only from a composed `ActivityConfig`'s own device list. This closes a real gap: switching from a Harmony Activity to a composed one had no way to know a device shared between them (e.g. a soundbar with only a `PowerToggle` command, no discrete on/off) was already on, and could send an unwanted toggle that turned it off instead of confirming it stayed on.
- Builder (`docs/js/cards.js`): a `scene_grid` tile with "Track as Activity" checked can now list which physical devices it involves (comma-separated ids) — mainly useful on a Harmony-backed tile, since Astrion has no other way to know which devices a Harmony Activity touches. `scene_grid` tiles also gained an IR device+command picker and a "Composed Activity" picker referencing the new Activities section.
- `MainActivity.kt`: `runHotkey()` now dispatches `irDevice`+`irCommand` bindings directly through the device's own IR blaster (`ConsumerIrManager`) — the same local IR path `scene_grid`/composed Activities already had, now available on physical-button bindings too. Closes the loop for a composed Activity's volume routing when the volume device is local IR.
- New `title` card type — a section header for grouping cards on a page (title + optional subtitle, independently alignable), ported from Home Assistant's Mushroom Title card. Where Mushroom uses its own `title_tap_action`/`subtitle_tap_action` (a full HA `ActionConfig` — call-service, navigate, more-info, url, assist...), this instead reuses the same `title_`/`subtitle_`-prefixed action fields `scene_grid` already has, so it also covers Harmony/IR/composed-Activity actions with nothing new to learn. Also supports an optional `icon` (a PNG file path, same `BitmapFactory.decodeFile` convention every other icon in the app uses — deliberately not a bundled/named vector set) and a `divider` line filling the rest of the row, Bubble-Card-style; either forces the title row left-aligned regardless of `alignment`, since that layout has no sensible centered/right-aligned form. An optional `color` (same ARGB hex convention as `scene_grid`'s) tints the title text and, when `divider` is on, the line at reduced alpha to match — the subtitle and icon are untouched by it, icons are never tinted anywhere in the app. Builder: new "Title" entry under "Common" with a title/subtitle/alignment/icon/divider/color form; a tappable title needs the "Other / custom type…" raw-JSON editor instead, since re-saving through the simple form — like every card type here — rewrites the card's options from scratch.

### Changed

- Builder: editing an existing Harmony-backed tile (`scene_grid` or `apple_tv_remote`) that has no explicit `hub` no longer silently defaults the Hub dropdown to the first configured hub — with more than one hub, that default could be the wrong one and would get silently re-saved as correct. The dropdown now shows empty and the existing "pick a hub" validation blocks saving until one is chosen explicitly.

Incorporates the `SettingsOverlay` fix from [PR #3](https://github.com/dckiller51/astrion-custom-dashboard/pull/3) (see Fixed, below), applied to `ActivitiesOverlay` as well.

### Fixed

- Builder (`docs/js/cards.js`): `fillGiHarmonySection()` was defined twice (dead duplicate); removed.
- Builder: `dashboard.json`'s `irDevices`/`activities` were silently dropped every time the builder reloaded a config — both `pages.js`'s "paste JSON" import and `device.js`'s auto-reload-from-device path had a field whitelist that pre-dated those two sections.
- Builder: the Activities section's IR-device picker didn't refresh after saving or removing an IR device (only the `scene_grid` form's picker did, via a different refresh path).
- `Dashboard.kt`: `SettingsOverlay` called `SettingsMenu(ctx, onClose = onClose)`, but `SettingsMenu` only ever declared `ctx` — a pre-existing compile error.
- `HaModels.kt`: `EntityState.attrString()`/`attrDouble()`/`attrBoolean()` used the throwing `.jsonPrimitive` extension on a raw attribute value, crashing the app on any non-primitive attribute instead of returning null — switched to a safe `as? JsonPrimitive` cast. Reported against v0.7.0 in [issue #2](https://github.com/dckiller51/astrion-custom-dashboard/issues/2) with a Kodi `media_player` entity, whose `media_content_id` attribute is a nested object (`{"imdb": "...", "tmdb": "..."}`) rather than the plain string most other media players report: the `media_player` card's progress bar crashed on `variant: "full"` once playback started, and crashed the long-press Detail dialog outright, both of which key their `remember`/`LaunchedEffect` on that attribute. `MediaPlayerCard.kt`/`MediaPlayerDetailDialog.kt` also switched that key from `attrString("media_content_id")` to `attr("media_content_id")?.toString()`, so the progress bar still resets correctly between tracks for Kodi (a plain `attrString()` would now just always read null for it, post-fix, since it's never a primitive) as well as for every player that reports it as a plain string.
- Top status bar clock now honors the device's 12/24h setting instead of always rendering 24h, and is centered to the full bar width rather than drifting with the Wi-Fi/battery glyph widths. `ConfigServer` no longer crashes with `EADDRINUSE` on connection save, and retries once on a delay if the initial `:8080` bind fails. An unmapped physical BACK press no longer destroys the launcher activity; saving new connection settings now reconnects HA/Harmony clients and restarts `ConfigServer` in place instead of relying on `Activity.recreate()`, which was unreliable on the HA100's Android 8.1. All three via [PR #3](https://github.com/dckiller51/astrion-custom-dashboard/pull/3), contributed by [@ClemsonJeeper](https://github.com/dckiller51/astrion-custom-dashboard/commits?author=ClemsonJeeper).

- **IR Activities**: named sequences of raw IR sends, executed locally through the device's own IR blaster (`ConsumerIrManager`) — no Harmony hub or Home Assistant required, for setups without one.
  - `AppConfig`: new `irActivities` list (`IrActivityConfig`/`IrStepConfig` — id/name/steps, each step a `freq`/`pattern`/optional `delayAfterMs`), parsed from `dashboard.json`'s new `"irActivities"` array.
  - `CardContext`: exposes `irActivities` (by id) to cards.
  - `SceneGridCard`: new `irActivity` scene action (alongside `entity_id`/`activityId`/`page`) — runs the named activity's steps in order on the card's own coroutine scope, waiting `delayAfterMs` between steps.
  - `docs/ir-database/`: community-contributed device codes (`index.json` category manifest + one JSON file per category, e.g. `tv.json`), keyed by category → brand → model → command, storing each command as Pronto Hex (universal raw IR timing, protocol-agnostic — works for NEC, JVC, Sony, etc. via one decoder instead of one per protocol).
  - `docs/index.html`: new "IR Activities" section — cascading Category → Brand → Model → Command pickers (loaded from `ir-database/`), per-step delay, and a Pronto → `freq`/`pattern` decoder that resolves each step at build time, so `dashboard.json` ships fully-resolved steps and the app never needs to parse a protocol or ship the database itself. `scene_grid` items gained an "IR activity" picker alongside their existing action fields.

### Changed

- `ClimateCard` / `FanCard`: power buttons now share a consistent color scheme — red when off, green when on — instead of `ClimateCard`'s off-only red accent and `FanCard`'s on-only green accent, so both cards read the same way at a glance.
- `docs/index.html`: `button_grid`/`scene_grid` items in the editor list can now be clicked to edit them in place, instead of only add/remove.
- `docs/index.html`: the small in-frame preview no longer shows the card type label, edit/remove icons, or `hint` text (entity id, "example data", etc.) — only the expanded modal does — since none of that renders on the real device.
- `docs/index.html`: split the single ~1400-line file into `styles.css` + `js/{mocks,pages,cards,hotkeys,ir,export,preview}.js`, matching the section comments that were already there. Same behavior, just easier to find and edit a given piece — and `docs/js/` now needs to be deployed alongside `index.html`, not just the one file.

### Fixed

- Wi-Fi sometimes failed to reactivate after a restart, requiring a manual trip into Android's system settings. Added a `WifiBootReceiver` (`BOOT_COMPLETED`) that re-enables Wi-Fi automatically at startup if it isn't already on, with the `ACCESS_WIFI_STATE`/`CHANGE_WIFI_STATE` permissions it needs to read and change the radio state.
- `docs/index.html`: `button_grid`/`scene_grid` cards with more columns than fit the small in-frame preview width caused a horizontal scrollbar; grid columns now shrink to fit instead.
- `SceneGridCard`: tile height (icon vs. text-only) was decided per-tile, so a grid mixing scenes with and without an `icon` rendered uneven row heights. It's now decided once for the whole grid — every tile matches as soon as any one of them has an icon.

### Changed

- `ClimateCard`: the "off" hvac mode no longer shows as a chip — the card's header already has a dedicated power-off button, so a chip for it was a redundant control.
- `ClimateCard`: mode chip rows (hvac/fan/swing) now wrap and balance evenly across rows (e.g. 5 items → 3+2) instead of a hard 4-per-row cutoff that silently hid anything past the 4th mode.
- `ClimateCard`: tightened padding/spacing and chip/button sizes to reduce the card's overall height on small panels.

### Fixed

- `ClockWeatherCard` didn't translate its current-condition label — it just capitalized the raw Home Assistant state string (e.g. `partlycloudy` → "Partlycloudy") instead of going through `HaLabels`. It now calls `HaLabels.weatherCondition()` like the rest of the app.
- `assets/ha_labels/*.json`'s `weather_condition` category only covered 10 of the 16 conditions Home Assistant's weather platform can report; added the missing `clear`, `lightning-rainy`, `snowy-rainy`, `windy-variant`, `hail`, and `exceptional` entries (English and French).
- `VacuumCard` had the same issue as `ClockWeatherCard`: its activity-state label (docked/cleaning/paused/idle/returning/error) was capitalized from the raw state instead of going through `HaLabels`. It now calls `HaLabels.vacuumState()`. Fan-speed/cleaning-mode names are left as-is since they're integration-specific, not a fixed HA value set.
- `ClimateCard`'s fan-mode chips were built from a hardcoded `["low", "medium", "high", "auto"]` guess whenever `dashboard.json` didn't override them, ignoring the entity's own `fan_modes` attribute — unlike `hvac_modes`, which already read it correctly. Chips could show options the device doesn't actually support (and silently fail when tapped). It now prefers the entity's reported `fan_modes`, falling back to the config override or the hardcoded list only if the integration reports nothing.
- `ClimateCard`'s current-temperature label ("Now 27°") was a hardcoded English string instead of going through `res/values*/strings.xml` like the rest of the app's UI text; added `climate_current_temp` (English and French) and switched the card to `stringResource()`.
- `ClimateCard`'s hvac-mode chips silently dropped anything past the 4th mode (`modes.take(4)`) — an entity reporting `off, fan_only, heat, cool, heat_cool, dry` only ever showed the first four. The cap is gone; see "Changed" above for the row-wrapping that replaces it.
